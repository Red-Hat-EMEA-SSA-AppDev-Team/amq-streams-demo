= Accessing Kafka outside of the OpenShift cluster

== Listener configuration and authentication

Those connection `type` exposes Kafka in the external listener configuration:

- `nodeport` uses a NodePort type Service
- `loadbalancer` uses a Loadbalancer type Service
- `ingress` uses Kubernetes Ingress and the Ingress NGINX Controller for Kubernetes
- `route` uses OpenShift Routes and the HAProxy router (the simplest method albeit not the most efficient)

Here we'll use `route` and `scram-sha-512` for authentication:

. Add external listener by adding this section to the existing Kafka resource:
+
[source,yaml]
----
    - name: external
      tls: true
      type: route      
      port: 9094
      authentication:
        type: scram-sha-512
----
+
Otherwise patch it with the following command:
+
[source,shell]
----
oc patch kafka my-cluster --type=json --patch '[{"op":"add","path":"/spec/kafka/listeners/-","value":{"authentication":{"type":"scram-sha-512"},"name":"external","port":9094,"tls":true,"type":"route"}}]'
----

WARNING: A merge patch replaces an entire list; do not use a merge patch containing only the `external` listener. The JSON patch above appends it and preserves the existing listeners.

If the old merge-patch command has already removed the internal listeners, restore the complete listener list (including the external listener) with:

[source,shell]
----
oc patch kafka my-cluster --type=merge --patch '{"spec":{"kafka":{"listeners":[{"name":"plain","port":9092,"type":"internal","tls":false},{"name":"tls","port":9093,"type":"internal","tls":true},{"name":"external","port":9094,"type":"route","tls":true,"authentication":{"type":"scram-sha-512"}}]}}}'
----

. Define a new user:
+
[source,shell]
----
oc apply -f k8s/30-user.yaml
----

. The client must trust the Kafka CA certificate to establish the encrypted connection. The following command **extract** the CA certificate and **create a truststore** for the Java clients:  
+
[source,shell]
----
oc get kafka my-cluster -o=jsonpath='{.status.listeners[?(@.name=="external")].certificates[0]}{"\n"}' > kafka-cluster-ca.crt
keytool -import -trustcacerts -alias root -file kafka-cluster-ca.crt -keystore truststore.jks -storepass password -noprompt
----

. Configure the Kafka consumer to run from your local environment and connect to the Kafka cluster on OpenShift. Client security is selected at runtime: `KAFKA_SECURITY_PROTOCOL=PLAINTEXT` (the default) uses an unsecured listener, while `SASL_PLAINTEXT` or `SASL_SSL` enables authentication. The same consumer and producer image supports either mode; provide the matching Kafka client environment variables when starting it.
+
[source,shell]
----
export KAFKA_BOOTSTRAP_SERVERS="$(oc get kafka my-cluster -o jsonpath='{.status.listeners[?(@.name=="external")].bootstrapServers}')"
export KAFKA_SSL_TRUSTSTORE_LOCATION=../truststore.jks
export KAFKA_SSL_TRUSTSTORE_PASSWORD=password
export KAFKA_SECURITY_PROTOCOL=SASL_SSL
export KAFKA_SASL_MECHANISM=SCRAM-SHA-512
export KAFKA_SASL_JAAS_CONFIG="$(oc get secret my-user -o jsonpath='{.data.sasl\.jaas\.config}' | base64 -d)"
----
+
NOTE: Quarkus converts environment variable names such as `KAFKA_SASL_MECHANISM` to Kafka client property names such as `kafka.sasl.mechanism`. Any Kafka client property can therefore be supplied this way. The authentication-specific variables are only needed when `KAFKA_SECURITY_PROTOCOL` is a SASL protocol.

. Start locally the kafka consumer:
+
[source,shell]
----
mvn -f kafka-consumer/pom.xml package quarkus:dev
----

Alternatively, you can use the console consumer shipped by the Kafka project.

Use the previous step command to create the `client.config` file (drop `kafka.` prefix). 
Then issue the following command:

[source,shell]
----
bin/kafka-console-consumer.sh \
--bootstrap-servers (oc get kafka my-cluster -o jsonpath='{.status.listeners[?(@.name=="external")].bootstrapServers}')
--topic event \
--consumer.config client.config
----

== Authorization

You can grant different permissions to your users.

There are 4 options:

- **Simple** authorization
- OAuth 2.0 authorization using Red Hat SSO
- Open Policy Agent (OPA) authorization
- Custom authorization


[TIP]
====
To ensure a clean environment, stop any running client:

[source,yaml]
----
oc scale deployment kafka-producer --replicas=0
oc scale deployment kafka-consumer --replicas=0
----
====

In this tutorial, you will configure the simple authorization:

. Enable the authorization in the Kafka resource:
+
[source,shell]
----
oc edit kafka my-cluster
----
+
Under `kafka` add `authorization` and the the authentication for each listener:
+
[source,yaml]
----
  ### kafka section
    authorization:
      type: simple
  ### for each listener add:
        authentication:
          type: scram-sha-512
----
+
The following script applies all the changes in one shot.
It's worth noticing that it does not change the third listener since it is already configured with the SCRAM authentication:
+
[source,shell]
----
oc patch kafka my-cluster --type=json --patch '[
{"op":"add","path":"/spec/kafka/authorization","value":{"type":"simple"}},
{"op":"add","path":"/spec/kafka/listeners/0/authentication","value":{"type":"scram-sha-512"}},
{"op":"add","path":"/spec/kafka/listeners/1/authentication","value":{"type":"scram-sha-512"}}]'
----
+
WARNING: When you enable the authorization all your listener have to authenticate their clients. In fact, authorization acts cluster wide, so you cannot accept anymore anonymous interactions.

. Edit the `kafkauser` resource
+
[source,shell]
----
oc edit kafkausers my-user
----
+
Add the following ACLs:
+
[source,yaml]
----
  # at spec level:
  authorization:
    type: simple
    acls:
    - resource:
        name: event
        patternType: literal
        type: topic
      operations:
      - Read
      - Describe
      - Write
      - IdempotentWrite
    - resource:
        name: '*'
        patternType: literal
        type: group
      operations:
      - Read
      - Write
----
+
The previous definition grants the main operations (read, write, etc) to the `event` topic and to all consumer groups.

. Wait a few minutes while the operator completes the rolling update of the Kafka brokers and the entity operator, then you can start the local consumer to check that it is still working properly, inspect the logs to spot potential error messages.
+
[source,shell]
----
mvn -f kafka-consumer/pom.xml package quarkus:dev
----

. To prove that ACL can block your user from reading, remove the `Read` operation and and execute again the the local consumer (check previous step).

. Stop the consumer and add back the `Read` operation in the ACL.

When authorization is enabled, configure the Kafka client environment of each application. This changes runtime configuration only: no new consumer or producer image is required. The base ConfigMaps set `KAFKA_SECURITY_PROTOCOL: PLAINTEXT`; replace it and add the following variables to both `kafka-producer-config` and `kafka-consumer-config`.

. Update both application ConfigMaps:
+
[source,shell]
----
oc edit configmap kafka-producer-config
oc edit configmap kafka-consumer-config
----
+
[source,yaml]
----
# In the data section of each ConfigMap, set the bootstrap service for the
# authenticated listener, replace KAFKA_SECURITY_PROTOCOL, and add the
# following properties:
  KAFKA_BOOTSTRAP_SERVERS: my-cluster-kafka-bootstrap:9092
  KAFKA_SASL_JAAS_CONFIG: |-
    org.apache.kafka.common.security.scram.ScramLoginModule
    required username="my-user" password="<PASSWORD>";
  KAFKA_SASL_MECHANISM: SCRAM-SHA-512
  KAFKA_SECURITY_PROTOCOL: SASL_PLAINTEXT
----
+
Replace `<PASSWORD>` with the output of: `oc get secret my-user -o jsonpath='{.data.password}' | base64 -d`

. Start again consumer and producer and check the logs to spot potential error messages:
+
[source,shell]
----
oc scale deployment/kafka-consumer --replicas=1
oc scale deployment/kafka-producer --replicas=1
oc logs --tail=20 -f --selector="app.kubernetes.io/name=kafka-producer"
----

== Quotas

=== Prerequisites

1. **Quota Plugin Type**: Ensure your Kafka cluster uses the built-in `kafka` quota plugin. The `strimzi` quota plugin applies only aggregate limits cluster-wide and does not support per-user quota overrides. The built-in `kafka` plugin is active by default unless explicitly configured otherwise.
2. **User Operator Running**: Ensure the User Operator is deployed as part of the `Entity Operator` in your `Kafka` custom resource to watch and manage `KafkaUser` resources.
3. **Cluster Reference Label**: Any `KafkaUser` resource must include the `strimzi.io/cluster: <cluster-name>` label identifying the Kafka cluster it belongs to.

=== Step 1: Verify the Kafka Cluster Quota Plugin

Check that your `Kafka` resource either does not define a quota plugin (defaulting to `kafka`) or explicitly configures the `kafka` plugin:

[source,yaml]
----
apiVersion: kafka.strimzi.io/v1
kind: Kafka
metadata:
  name: my-cluster
spec:
  kafka:
    # ...
    quotas:
      type: kafka
----

=== Step 2: Define or Update the `KafkaUser` Resource

Configure the `spec.quotas.producerByteRate` property in the `KafkaUser` resource for `my-user`. The `producerByteRate` property defines the maximum number of bytes per second that the client can publish to each broker before produce requests are throttled.

Edit `my-user`:

[source,shell]
----
oc edit kafkausers my-user
----

add the quotas section:

[source,yaml]
----
apiVersion: kafka.strimzi.io/v1
kind: KafkaUser
metadata:
  name: my-user
  labels:
    strimzi.io/cluster: my-cluster     # Matches the name of your Kafka custom resource
spec:
  authentication:
    type: scram-sha-512|
  quotas:
    producerByteRate: 10000         # Limit to 1 10000 bytes/sec per broker
    # Optional additional quota properties:
    # consumerByteRate: 2097152       # Limit fetch rate to 2 MB/s per broker
    # requestPercentage: 50           # Limit CPU utilization across network & I/O threads
----

* `producerByteRate`: Value in bytes per second (for example, `1048576` = 1 MB/s, `10485760` = 10 MB/s) applied on a per-broker basis.
* `consumerByteRate` / `requestPercentage`: Optional additional parameters to limit fetch throughput or broker CPU processing time.


The **User Operator** detects the resource update and automatically applies the quota to the user principal inside the Kafka cluster.

---

=== Step 3: Verify the Quota Configuration

. Check the status of the `KafkaUser` resource to ensure reconciliation succeeded:
+
[source,shell]
----
oc get kafkauser my-user -o yaml
----
+
Verify that under `status.conditions`, the condition type `Ready` is `True`.

. *(Optional)* In the **Streams for Apache Kafka Console**, navigate to the **Kafka Users** page, select `my-user`, and inspect the user's details and configuration.


=== Alternative: Enabling quotas on RHEL

For deployments running directly on RHEL or when modifying user quotas via the Kafka Admin CLI without the User Operator, use the `kafka-configs.sh` utility:

[source,shell]
----
/opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server <bootstrap_address>:9092 \
  --entity-type users \
  --entity-name my-user \
  --alter \
  --add-config producer_byte_rate=1048576
----

To verify the updated configuration:

[source,shell]
----
/opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server <bootstrap_address>:9092 \
  --entity-type users \
  --entity-name my-user \
  --describe
----

----
oc scale deployment/kafka-producer --replicas=0
oc apply -f k8s/01-kafka-metrics.yaml

oc apply --force -f kafka-consumer/src/main/kubernetes/openshift.yml
oc delete configmap kafka-producer-config
oc apply --force -f kafka-producer/src/main/kubernetes/openshift.yml
----
